Act as an expert Software Engineering researcher specialized in the analysis of automated code reviews.

I have attached a CSV file containing a series of code review comments generated by an AI agent. The file contains the following columns:

- `id`: the comment id
- `repo`: name of the GitHub repository (use it as context about the project/language/framework).
- `comment_text`: the text of the review comment generated by the AI agent.

#### OBJECTIVE

Semantically analyze every single comment in the CSV and classify it into exactly ONE of the 16 categories of the taxonomy below. If a comment genuinely does not fit any of them, you may propose a new category instead (see Classification Rule 2).

IMPORTANT: Do not use Python scripts based on keyword matching or regular expressions to classify the comments automatically. You must read and evaluate the meaning and technical intent of each comment.

---

#### CATEGORY TAXONOMY (Use exactly these names)

1. **Bugs, Robustness, and Error Handling**: Functional defects, logic errors, null/undefined dereferences, unhandled exceptions, edge cases, input validation, or missing defensive checks.
2. **Documentation**: Missing, outdated, inaccurate, or unclear code comments, docstrings, Javadoc, README, or API documentation.
3. **Performance, Memory, and Multithreading**: Algorithmic inefficiencies, unnecessary allocations, memory/resource leaks, race conditions, deadlocks, synchronization issues, or thread-safety problems.
4. **Cloned, Deprecated, Unneeded, and Commented-out Code**: Dead code, unused imports/variables, duplicated code blocks, commented-out code, or use of deprecated APIs/methods.
5. **Software-specific**: Domain-specific rules, particular framework/library conventions of the `repo`, or project-specific architectural constraints that do not concern standard programming practices.
6. **Testing**: Missing unit/integration tests, weak assertions, faulty test setup/fixtures, test isolation problems, or fragile tests.
7. **Logging and Error/Testing Messages**: Missing or excessive logs, incorrect log levels, uninformative exception messages, or unclear assertion error messages.
8. **Code Design Principles**: Violations of design/OOP principles (e.g., SOLID, high coupling, low cohesion, wrong abstraction, poorly distributed responsibilities, or poor modularity).
9. **Hardcoded Data**: Magic numbers, hardcoded strings, paths, URLs, timeouts, or environment-specific values that should be parameterized or extracted into constants/configuration.
10. **Understandability**: Overly complex expressions, convoluted control flow, or code that is hard for a human maintainer to read and understand (excluding mere formatting/naming).
11. **Formatting, Style, and Identifiers**: Indentation, whitespace, brace placement, naming conventions, typos in variable/method/class names, or style-guide/linter violations.
12. **Build Process, Dependencies, and Configurations**: Problems in build scripts (Maven, Gradle, Make, etc.), CI/CD pipelines, package versions, dependency declarations, or configuration files.
13. **Behavioral Changes**: Unintentional modifications or breaking changes to existing external behavior, public APIs, return values, default semantics, or backward compatibility.
14. **Maintenance**: General observations on maintainability, technical debt, or suggestions to ease the future evolution of the codebase.
15. **Clarification Questions**: Questions addressed to the author to clarify the intent, logic, or expected behavior of a change, without directly reporting a defect.
16. **Security**: Vulnerabilities, injection risks, improper authentication/authorization, insecure cryptography, sensitive data exposure, or unsafe deserialization.

---

#### CLASSIFICATION RULES

1. **Primary intent**: Base the classification on the main problem or the central corrective action requested by the AI agent, also taking into account the context of the `repo`.
2. **No suitable category (`None`)**: If you believe a comment does not fit any of the 16 categories:&#x20;
   - Set the category to `"None"`.
   - In `suggested_category`, write the name of the new category you think it should belong to.
   - In the `rationale`, explain both why none of the 16 existing categories is suitable and why the proposed category is correct.
3. **Confidence (Optional)**: Indicate the confidence level (`High`, `Medium`, `Low`), especially for borderline cases between two categories.

---

#### OUTPUT FORMAT

Return the complete result (without skipping or truncating any rows) as a table (or a downloadable CSV file) with the following columns:

- `id`: the original comment ID
- `repo`: the repository name
- `category`: the exact name of one of the 16 categories (or `None`)
- `suggested_category`: leave empty (`-`) if it falls within the 16 categories, otherwise write the proposed new category
- `confidence`: `High`, `Medium`, or `Low` (optional)
- `rationale`: brief justification (1-2 sentences) for the choice or for why it does not fit any category
